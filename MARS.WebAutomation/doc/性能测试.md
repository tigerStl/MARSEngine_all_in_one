# 性能测试使用说明

本文档说明在 MARS.WebAutomation 中如何录制、设计与可视化性能测试锚点（Performance Test Anchors）。

## 1. 快速开始

1. 启动并连接浏览器，进入目标业务页面。
2. 在工具栏勾选 `With Performance Test`。
3. 开始录制 UI 步骤（例如登录、创建业务对象）。
4. 系统会同步捕获协议请求（含 URL/Method/Type/Status/Header/Payload/Response）。
5. 在底部 `Perform Test anchors` 区域设计锚点：
   - `Promote`：提升为事务锚点
   - `Ignore`：标记为噪音请求
   - `Unlink`：解除与当前 UI 步骤关联
6. 双击任一请求打开 `Performance Request Detail` 进行参数化与锚点属性编辑。

## 2. Anchor（测试锚点）含义

- Anchor 是“需要被统计、回放、断言”的关键请求节点，类似 LoadRunner/JMeter 中的事务边界关键请求。
- 系统会自动给每条请求计算 `AnchorScore` 并给出 `AnchorCandidate` 建议。
- 用户可最终确认 `IsAnchorSelected`，并将其归入 `AnchorGroup`（如 Login、CreateApplication）。

## 3. 表格字段说明

- `Action`：当前可执行操作（Promote / Ignore / Unlink）
- `Anchor`：是否已选为锚点
- `Score`：系统自动评分（越高越可能是关键请求）
- `Group`：锚点所属事务组
- `Correlation`：是否建议做相关性处理（token/cookie/csrf 等）
- `URL`：请求地址
- `Type`：资源类型（xhr/fetch/document/image/...）
- `Method`：HTTP 方法
- `Status`：响应状态码
- `Parameter`：URL 参数摘要（query）
- `Header`：请求头摘要
- `Cookie`：cookie 摘要
- `Payload`：请求体
- `Response`：响应文本（用于断言）
- `ReplayPolicy`：回放策略建议（Keep/Ignore）
- `ValidationHint`：断言建议（状态码、关键字段、页面跳转等）

## 4. 详情窗口（Performance Request Detail）

详情窗口采用标签页（Tab）组织：

- `Headers`：头部详情
- `Payload`：请求体详情
- `Response`：响应详情
- `Parameterization`：参数化助手（可提取键并生成 `${var}` 占位）
- `Preview`：当 Type=image 时可尝试预览图片

顶部区域显示锚点元信息（Method、Type/Status、Anchor、Group、ReplayPolicy、ValidationHint、Correlation、Notes）。

## 5. 可视化区域说明

- UI 测试步骤仍以原有节点展示。
- 性能锚点按 `Group` 绘制为独立区域（anchor lane），并使用与 UI 节点不同的菱形形状。
- 已选锚点与候选锚点使用不同颜色，避免与 UI 流图重叠。

## 6. 设计建议

- 登录流建议至少保留：登录提交 + redirect/document + 首个关键业务请求。
- 创建业务流建议保留：页面初始化关键 xhr/fetch + 提交 create 请求。
- 静态资源（css/js/image/font）通常应忽略，除非专项测试前端资源链路。
- 对 token/cookie/csrf 等动态值，务必做相关性提取与回填。

## 7. Performance Pack 导出 / 导入（开放 JSON）

用于在团队、CI 或外部工具之间交换性能锚点数据，导入后可使用菜单 **Performance → Run NBomber**（或工具栏 **Run Perf**）执行压测。

### 7.1 入口

- 菜单：**Performance → Export Performance Pack…** / **Import Performance Pack…**
- 性能请求表：右键 **Export Performance Pack…** / **Import Performance Pack…**

### 7.2 完整格式（`mars.perf-pack/1.0`）

根对象字段：

| 字段 | 说明 |
|------|------|
| `schemaVersion` | 固定建议为 `mars.perf-pack/1.0` |
| `exportedAtUtc` | 导出时间（UTC），保存时自动写入 |
| `sourcePageUrl` | 可选，录制时的页面 URL |
| `defaultSimUsers` | 可选，默认模拟用户数 |
| `defaultDurationSeconds` | 可选，默认压测时长（秒） |
| `notes` | 可选备注 |
| `requests` | **数组**，元素与界面中的 `PerformanceRequestRecord` 字段一致（`id`、`url`、`method`、`anchorGroup` 等） |
| `transactionConfig` | 可选，按事务名（AnchorGroup）配置：`enabled`、`usersOverride`、`durationSecondsOverride`、`weight` |

### 7.3 极简 interchange（仅请求列表）

以下两种也会被 **Import** 识别：

1. 根为 JSON **数组**：直接作为 `requests`。
2. 根为对象且仅含 **`requests`** 数组：与完整格式兼容，其余字段省略。

缺少 `id` 的请求在导入时会自动生成新的 `id`。导入后会用新的 id 集合**清理**各 UI 步骤上已失效的 `PerformanceRequestRefs`，避免指向旧数据。

### 7.4 最小示例（仅 requests）

```json
{
  "schemaVersion": "mars.perf-pack/1.0",
  "requests": [
    {
      "id": "example-1",
      "method": "GET",
      "resourceType": "xhr",
      "url": "https://example.com/api/health",
      "anchorGroup": "General",
      "isAnchorSelected": true,
      "isFiltered": false
    }
  ]
}
```

## 8. 运行压测（NBomber）与实时监控

在 **Performance → Run NBomber**、工具栏 **Run Perf** 或 **Run Selected AnchorGroup** 时，会先弹出 **Performance run options**：

- **Concurrent users**：并发用户数（写入本次 `NBomber` 计划并同步到工具栏 Sim Users）。
- **Duration (seconds)**：压测持续时间。
- **Chart sample interval (sec)**：实时图横轴采样间隔（秒），每个间隔在图上追加一组柱状统计。
- **Save each response under data\\test\\log**：勾选后每个 HTTP 响应写入 `{DataRoot}/data/test/log/` 下的文本文件（含 URL、状态码、正文）。
- **Body must contain (optional)**：若填写，则仅当 **HTTP 状态码在 200–299** 时，还要求响应正文包含该子串（忽略大小写）；与状态码断言同时满足才算该请求成功。

确认后开始执行，并打开 **Performance live chart** 非模态窗口：

- **横轴上方**：按采样间隔显示五组柱（Created / Returned / Total 累计高度归一 / Errors / Success 的桶内增量）。
- **横轴下方**：圆角矩形统计区，显示 **最短 / 最长 / 平均** 响应时间（毫秒）与 **成功率**（及累计完成/成功/失败数）。

测试结束图表窗口自动关闭。

## 9. 并发量定义与容量判断（重要）

### 9.1 本工具中的并发含义

- `Concurrent users = N` 表示同一时刻有 **N 个虚拟用户**在执行事务。
- 当前执行模型采用 NBomber `KeepConstant`：在设定时长内，每个虚拟用户会**持续循环发送请求**，并非“每用户只发一次”。
- 因此 `TotalRequest` 是该时间窗内累计发起请求数，受到响应时延、网络、服务端处理速度影响，不是固定公式值。

### 9.2 阶梯并发（Stepped）如何理解

例如 `init=30, step=5, duration=60s`：

- 第 1 轮：30 并发跑 60 秒
- 第 2 轮：35 并发跑 60 秒
- ...
- 直到总并发上限

每轮都会产出真实统计（成功、失败、时延、吞吐）。`TotalRequest`/`Finished` 使用运行时真实计数，不是预估值。

### 9.3 如何判断“服务器可承载并发”

建议使用固定时间窗（如 60 秒）逐步加并发，重点看：

- 失败率（Fail / Error Rate）
- 延迟分位（P95、P75、P50）
- 吞吐变化趋势（Throughput）

当并发继续增加出现明显拐点（失败率上升、P95突增、吞吐不再增长甚至下降）时，可将拐点前一档视为稳定承载区间。
